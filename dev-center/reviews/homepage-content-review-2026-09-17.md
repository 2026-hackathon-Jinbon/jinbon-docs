# 진본 홈페이지 내용 검토와 개편 문안

검토일: 2026-09-17. 대상: 로컬 `jinbon-backend`, `jinbon-ios`, `jinbon-web`, `jinbon-extension`, `jinbon-docs`의 문서와 주요 구현.

이 문서는 홈페이지 개편을 위한 내용 검토와 제안이다. 실제 배포 상태·외부 인증 연동·검증 성능을 실험으로 확인한 보고서는 아니다. 웹 화면을 변경하거나 배포하지 않았다. 홈페이지는 `jinbon-docs/dev-center`, 검증 도구는 `jinbon-web`으로 구분한다. ZIP 백업은 별도 제품으로 계산하지 않았다.

## 1. 핵심 판단

진본의 중심 가치는 **영상의 등록자·등록 기록과 등록 영상과의 관계를 함께 확인할 근거를 제공하는 것**이다.

홈페이지는 다음 질문에 순서대로 답하는 편이 좋다.

1. 이 영상을 믿고 공유하기 전에 무엇을 확인해야 하는가?
2. 진본으로 어떤 근거를 확인할 수 있는가?
3. 등록하는 사람과 확인하는 사람은 각각 무엇을 하는가?
4. 검증 결과는 어떤 의미이며 어디까지 믿을 수 있는가?
5. 지금 어디에서 사용할 수 있는가?

현재 홈페이지에는 기술 설명과 한계 안내가 상당히 잘 갖춰져 있다. 다만 필요성을 구체적으로 보여주는 사례와 사용 과정이 약하고, 해시 이름·알고리즘·저장소 이름이 너무 일찍 등장한다. 기술을 추가로 나열하기보다 정보 순서를 바꾸는 것이 우선이다.

추천 서비스 정의:

> 진본은 본인확인을 마친 등록자의 영상 기록을 남기고, 확인하려는 영상과 등록 영상의 비교 결과를 제공하는 서비스입니다.

추천 핵심 문장:

> 영상을 믿고 공유하기 전, 등록 기록부터 확인하세요.

`출처 확인`을 사용할 때는 바로 다음 문장에서 출처의 의미를 `진본에 등록한 사람과 등록 기록`으로 한정한다. 최초 촬영자나 공식 배포처까지 확인한다는 인상을 피한다.

## 2. 전체 프로젝트를 사용자 관점에서 정리

| 프로젝트 | 실제 역할 | 홈페이지에서 전달할 내용 |
|---|---|---|
| jinbon-ios | 본인확인, 계정과 Wallet DID 연결, 영상 등록, 보증서 발급·보관, 등록 목록, 파일 검증 | 영상을 등록하고 등록 보증서를 관리하는 앱. 현재 사이트에는 배포 준비 중으로 안내됨 |
| jinbon-web | 파일 업로드와 URL 입력으로 공통 검증 API 호출, 결과·등록자 표시명·시점·확인 방식 표시 | 설치 없이 영상을 확인하는 웹 도구 |
| jinbon-extension | YouTube·Instagram 지원 페이지에 버튼 표시, 현재 URL을 백엔드에 전송 | 보고 있는 영상 페이지에서 검증 시작. 현재 안내는 ZIP 수동 설치 |
| jinbon-backend | 본인확인 연동, 등록, 영상·음성 비교, 블록체인·VC 확인, 캐시, 카카오톡 스킬 API | 각 이용 경로에 공통 검증 기준을 제공하는 서버 |
| jinbon-docs | 제품 소개, 사용 사례, 검증 상태, 시작 안내, 개발자 문서 | 서비스를 이해하고 자신에게 맞는 이용 경로를 찾는 홈페이지 |

카카오톡은 별도 `jinbon-*` 저장소가 아니라 백엔드의 `KakaoSkillController`에 구현되어 있다. 코드 존재와 실제 채널에서의 응답 성공은 구분해야 한다.

### 구성은 기술 이름보다 역할로 설명

| 구성 요소 | 답하는 질문 | 쉬운 설명 |
|---|---|---|
| 모바일 신분증 본인확인 | 등록할 계정의 본인확인을 마쳤는가? | 본인확인을 마친 회원이 영상을 등록합니다 |
| DID와 Wallet | 등록 계정과 보증서를 어떻게 연결하는가? | 등록자의 디지털 식별자와 보증서를 관리합니다 |
| 파일 해시 | 등록한 파일과 같은가? | 파일 전체에서 계산한 디지털 지문을 비교합니다 |
| 영상·음성 지문 | 파일이 달라도 등록 영상과 대응하는가? | 대표 장면과 음성 지문을 비교합니다 |
| 블록체인 | 대조할 등록 기록이 있는가? | 영상의 대표 지문과 등록자 식별자 등을 기록합니다 |
| 등록 보증서(VC) | 보증서가 이 등록 기록과 연결되고 유효한가? | 등록자와 해당 영상의 등록 정보를 담은 보증서를 확인합니다 |

## 3. 실제 구현으로 확인한 검증 흐름

### 등록

본인확인 → 계정과 Wallet DID 연결 → 영상 선택·업로드 → 파일·영상·음성 지문 계산 → 대표 지문의 블록체인 등록 → Wallet에서 동의·PIN 인증 후 보증서 수령 → 서버가 보증서와 영상의 연결 확인.

영상 등록과 보증서 발급은 별도 단계다. 등록이 끝났더라도 보증서가 미발급이면 최종 검증 완료 조건을 충족하지 못한다. 발급 실패·취소 후에도 등록 기록은 유지되며 재발급 절차를 진행할 수 있다.

### 검증

1. 파일을 업로드하거나 지원 URL을 제출한다. URL은 서버가 영상을 내려받아 분석한다.
2. 파일 전체의 SHA-256으로 정확히 일치하는 등록 기록을 찾는다.
3. 정확 일치가 없으면 지각해시로 등록 후보를 찾고, 대표 프레임과 음성 지문을 비교한다.
4. 유사도 경로는 영상 대응 비율 95% 이상, 음성 대응 비율 90% 이상, 순서 보존, 영상·음성의 동일한 원본 대응 시간 오프셋을 요구한다.
5. 선택된 등록 영상의 활성 상태, 온체인 기록과 서버 HMAC 대조, VC 상태와 등록 정보의 연결을 확인한다.
6. 비교 결과와 등록 증거가 모두 조건을 만족하면 `authentic=true`가 된다.

정확 일치는 무음 파일도 가능하다. 파일이 다른 유사도 경로는 음성 비교 정보가 없으면 승인하지 않는다. 짧게 잘라낸 영상도 먼저 후보 검색에 성공해야 하며, 모든 쇼츠를 찾는다고 말할 수 없다.

캐시된 결과를 반환하는 경로가 있으므로 모든 요청마다 블록체인과 보증서를 새로 조회한다고 설명해서는 안 된다. 현재 Redis 구현의 TTL은 10분이다.

### 이해를 돕는 예

등록자가 발표 영상을 진본에 등록한 뒤 다른 플랫폼에도 올렸다고 가정한다.

- 같은 파일을 제출하면 파일 지문으로 정확 일치를 확인할 수 있다.
- 플랫폼에서 재인코딩한 파일은 지문이 달라질 수 있다. 이때 영상·음성 비교 경로로 넘어간다.
- 일부 구간만 잘라낸 영상은 후보 검색과 비교 기준을 통과할 때 대응 구간을 확인할 수 있다. 생략된 앞뒤 맥락은 별도로 살펴야 한다.
- 등록 기록을 찾지 못하면 현재 비교할 근거를 찾지 못한 것이다. 조작 여부를 확정하는 결과가 아니다.

위 설명은 기능을 이해하기 위한 가정이며 실측 시연 결과가 아니다.

## 4. 현재 문안에서 고칠 부분

| 우선순위 | 현재 표현·구조 | 문제 | 수정 방향 |
|---|---|---|---|
| 높음 | “모바일 신분증 기반 공인 영상 진본 증명 플랫폼” | 공적 인증, 기관 권한 인증으로 읽힐 수 있음. 구현에서는 가입을 완료한 회원이 등록 권한을 가짐 | “영상의 등록 기록과 비교 결과를 확인하는 서비스” |
| 높음 | “원본”을 설명 없이 반복 | 촬영 원본·최초 제작물로 오해할 수 있음 | 기본 용어는 “등록 영상”, 파일 비교에서는 “등록 파일” |
| 높음 | “진본 확인 완료” 하나로 두 비교 방식을 묶음 | 정확 일치와 샘플 기반 유사도 사이의 차이가 약해짐 | 결과 제목 바로 아래에 “등록 파일과 정확 일치” 또는 “영상·음성 비교 기준 통과”를 크게 표시 |
| 높음 | “서버에 저장하지 않습니다”, “해시만 남김” | 분석 중 임시 파일을 생성하며 등록 정보·지문·보증서 관련 데이터도 보관함 | “영상은 분석을 위해 서버로 전송됩니다. 원본을 장기 보관하지 않으며, 분석용 임시 파일은 처리 후 삭제합니다” |
| 높음 | 홈페이지의 “카카오톡에서 바로”와 구성 카드의 “백엔드 배포 후 동작” | 이용 가능 상태가 한 페이지 안에서도 불일치 | 실제 채널 E2E 확인 후 하나의 상태로 통일 |
| 높음 | 개발자 문서 “웹은 파일 업로드만”, “URL 검증은 웹에서 쓰지 않음” | 현재 `page.tsx`에는 URL 입력·호출 구현이 있음 | 파일·URL 모두 설명. README도 함께 맞춤 |
| 중간 | 해시 구조와 95%·90%를 초반에 배치 | 사용자 가치가 늦게 드러나고 정확도 수치로 오해할 수 있음 | 알고리즘과 수치는 검증 원리 상세로 이동 |
| 중간 | 시스템 카드에 저장소·언어·프레임워크 나열 | 일반 방문자의 선택에 도움이 적음 | “등록하는 앱 / 확인하는 웹 / 영상 페이지의 확장”으로 표현 |
| 중간 | “영상 검증하기” 버튼이 다운로드 안내로 이동 | 버튼이 예고한 행동과 도착 화면이 다름 | 주 버튼은 검증 웹, 보조 버튼은 원리 또는 등록 안내 |
| 중간 | “즉시 검증”, “즉시 확인” | URL 다운로드와 분석 시간이 필요하며 처리시간 측정 근거가 없음 | “검증 시작”, “분석 후 결과 확인” |
| 중간 | 사용 사례의 “추적 불가”, “표준화된 방법 없음” | 다른 기술·방법을 포괄적으로 부정하는 근거가 없음 | “등록 기록과 비교 근거를 함께 확인하기 어렵습니다”처럼 사용자의 문제를 구체화 |
| 중간 | “등록 시점이 블록체인에 확정” | API 표시 시각은 DB 생성 시각이며 컨트랙트 시각과 별개 | 화면에는 “진본 등록 시각”. 온체인 시각을 별도로 제공할 때 구분 |

등록자 표시명은 회원이 수정할 수 있으므로 기관명처럼 보여도 기관 소속이나 공식 발행 권한을 인증했다는 뜻이 아니다. 홈페이지·검증 도구·확장·앱에 같은 용어를 적용해야 한다.

## 5. 추천 홈페이지 구성과 바로 쓸 수 있는 문안

### 첫 화면 — 서비스의 약속

작은 소개: **영상 등록·검증 서비스, 진본**

제목:

> 영상을 믿고 공유하기 전,
> 등록 기록부터 확인하세요.

설명:

> 누가 언제 등록한 영상인지, 지금 보는 영상이 등록 영상과 어떻게 일치하는지 확인하세요. 진본은 영상 비교 결과와 블록체인 등록 기록, 등록 보증서를 함께 확인합니다.

주 버튼: **영상 확인하기** → 검증 웹

보조 버튼: **검증 원리 알아보기** → 아래 검증 원리

짧은 안내: **사전에 진본에 등록된 영상을 기준으로 비교합니다. 웹 검증은 로그인 없이 이용할 수 있습니다.**

옆에는 실제 결과 화면의 구조를 보여주는 예시 카드를 둔다. “결과 예시”라고 명확히 표시하고, 가상의 기관 인증 배지나 실측하지 않은 성능 수치를 사용하지 않는다.

### 필요성 — 공유된 영상에 확인할 기준을 더합니다

제목:

> 공유된 영상, 무엇을 기준으로 확인하시나요?

본문:

> 다른 계정이 다시 올린 영상이나 짧게 잘린 영상을 접하면, 누가 등록한 영상인지와 어떤 기록을 기준으로 비교해야 하는지부터 궁금해집니다. 진본은 등록할 때 남긴 기록을 바탕으로, 나중에 접한 영상과의 관계를 확인할 수 있게 합니다.

세 가지 질문:

- **누가 등록했나요?** 본인확인을 마친 등록자의 식별 정보와 등록 기록을 확인합니다.
- **등록 영상과 같나요?** 파일이 정확히 같은지 확인하고, 파일이 다르면 영상과 음성 지문을 비교합니다.
- **확인 근거가 있나요?** 블록체인 등록 기록과 그 기록에 연결된 보증서의 유효성을 확인합니다.

### 사용 과정 — 등록할 때 남긴 근거를, 확인할 때 꺼내봅니다

등록하는 사람:

1. **본인확인** — 앱에서 본인확인을 마치고 디지털 지갑을 연결합니다.
2. **영상 등록** — 영상을 선택하면 디지털 지문을 계산해 블록체인에 등록합니다.
3. **보증서 수령** — 지갑에서 발급 절차를 완료하고 등록 보증서를 보관합니다.

확인하는 사람:

1. **파일 또는 링크 선택** — 웹에서 영상 파일을 올리거나 지원하는 영상 링크를 입력합니다.
2. **영상과 기록 대조** — 등록 영상을 찾아 비교하고 등록 기록과 보증서를 확인합니다.
3. **근거와 함께 결과 확인** — 비교 방식, 등록자 표시명, 등록 시각, 확인하지 못한 이유를 살펴봅니다.

앱 안내에는 현재 공개 상태인 “배포 준비 중”을 함께 표시한다. 등록자가 원본 파일을 직접 보관해야 한다는 점도 등록 안내에 포함한다.

### 검증 원리 — 세 가지 근거를 함께 확인합니다

**영상 비교: 등록된 영상과 어떤 관계인가요?**

> 먼저 파일 전체의 디지털 지문을 비교합니다. 파일이 다르면 대표 장면과 음성 지문을 비교해 등록 영상과 대응하는지 확인합니다.

**등록 기록: 비교 기준이 되는 기록이 있나요?**

> 블록체인에 남긴 대표 지문과 등록자 식별자, 기록의 활성 상태 등을 대조합니다.

**등록 보증서: 이 등록 정보에 연결된 보증서가 유효한가요?**

> 등록 보증서의 상태와 발급자·등록자 정보, 해당 영상의 등록 기록과 연결되는 내용을 확인합니다.

짧은 결론:

> 영상 비교와 등록 증거 확인을 모두 통과해야 검증 완료로 표시합니다.

상세 설명 링크: **파일 비교와 영상·음성 비교의 차이 보기**

기술 명칭은 카드 하단에 보조 정보로 넣는다. 모바일 신분증 → 본인확인, OmniOne Chain → 등록 기록, Open DID → 등록 보증서로 연결한다.

### 결과 읽기 — 배지와 확인 방식을 함께 보세요

| 화면에 보여줄 정보 | 설명 문안 |
|---|---|
| 등록 파일과 정확 일치 | 파일 전체의 디지털 지문이 같고, 등록 기록과 보증서가 유효합니다 |
| 영상·음성 비교 기준 통과 | 비교한 대표 장면과 음성 지문이 기준을 충족하고, 등록 기록과 보증서가 유효합니다. 파일 전체가 같다는 뜻은 아닙니다 |
| 유사한 등록 영상 발견·확인 보류 | 등록 후보는 찾았지만 비교 기준을 충족하지 못했거나 정보가 부족합니다 |
| 등록 기록을 찾지 못함 | 현재 비교할 수 있는 등록 기록을 찾지 못했습니다. 가짜라는 뜻은 아닙니다 |
| 등록·보증서 상태 확인 필요 | 등록이 비활성화되었거나 보증서가 없거나 유효하지 않습니다. 상세 사유를 확인하세요 |
| 현재 확인할 수 없음 | 외부 연결 문제 또는 등록 기록의 검증 문제로 확인을 완료하지 못했습니다. 안내된 사유에 따라 재시도하거나 운영자 확인이 필요합니다 |

위 표는 제안하는 설명 체계다. API 상태 코드를 변경하자는 뜻은 아니다. 현재 공통 배지인 “진본 확인 완료”를 유지하더라도 확인 방식은 제목과 같은 시선 흐름에 배치한다. “확인 중”은 자동으로 처리가 계속되는 듯하므로 완료된 장애 응답에는 “현재 확인할 수 없음”이 적합하다.

### 사용 사례 — 실제 도입 성과와 구분한 활용 예

**보도·발표 영상을 전달할 때**

> 공개할 영상을 미리 등록해 두면, 전달받은 사람이 등록 기록과 영상 비교 결과를 확인할 수 있습니다. 소속 기관과 공식 발표 권한은 별도로 확인해야 합니다.

**제작한 영상을 여러 플랫폼에 공유할 때**

> 플랫폼 게시 전에 등록 기록을 남겨두고, 유통된 영상이 등록 영상과 어떻게 대응하는지 확인할 수 있습니다. 재인코딩된 영상은 후보 검색과 영상·음성 비교 기준을 충족해야 합니다.

**업무 현장의 기록을 주고받을 때**

> 같은 파일을 전달했는지 확인할 비교 기준을 남기고, 등록 시점과 등록자를 함께 확인할 수 있습니다. 원본 파일은 직접 보관하세요.

법원 제출·저작권 분쟁의 해결을 대표 성과처럼 제시하지 않는다. 현재 기능 설명만으로 증거 채택이나 소유권을 보장할 근거는 없다.

### 마지막 안내 — 결과를 더 정확하게 이해하려면

FAQ로 다음 내용을 짧게 제공한다.

**등록 영상이면 내용도 사실인가요?**

> 진본이 확인하는 것은 등록 기록과 영상의 비교 결과입니다. 영상 속 사건의 사실성, 촬영 원본 여부, AI 생성 여부, 제작자·저작권자 여부까지 보증하지는 않습니다.

**등록한 사람은 공식 기관의 담당자인가요?**

> 등록 계정의 본인확인과 기관의 공식 권한 확인은 별개입니다. 등록자 표시명만으로 소속이나 직함이 인증되는 것은 아닙니다.

**영상 파일은 어떻게 처리하나요?**

> 영상은 분석을 위해 서버로 전송됩니다. 원본을 장기 보관하지 않으며, 분석용 임시 파일은 처리 후 삭제합니다. 등록한 영상의 지문과 등록 정보 등은 검증에 사용됩니다.

**등록 시각은 촬영 시각인가요?**

> 진본에 등록된 시각입니다. 촬영하거나 제작한 시각을 의미하지 않습니다.

**등록 기록이 없으면 가짜인가요?**

> 현재 진본에서 비교할 등록 기록을 찾지 못했다는 뜻입니다. 그 결과만으로 조작 여부를 판단할 수 없습니다.

마지막 행동 유도:

> 확인할 영상이 있나요?
> 파일이나 링크로 등록 기록과 비교 결과를 살펴보세요.

## 6. 품질을 높이는 화면 편집 기준

- 첫 화면에는 가치 문장, 서비스 설명, 주 행동 하나, 결과 예시 하나를 둔다.
- 도식은 “등록자 → 등록 기록·보증서 → 확인하는 사람” 순으로 만든다. 서버 이름·포트는 개발자 문서로 이동한다.
- 결과 예시는 정확 일치와 영상·음성 비교를 나란히 보여준다. 둘의 설명과 확인 방식 차이가 즉시 보여야 한다.
- 숫자 대신 확인 가능한 근거를 강조한다. `95%·90%`는 상세 기준에만 두고 정확도라는 단어와 함께 사용하지 않는다.
- 원리 설명과 한계 안내를 반복하지 않는다. 결과 해석에 필요한 한계는 결과 옆에, 나머지는 FAQ와 검증 상세에 둔다.
- `공인 등록자`는 `본인확인을 마친 등록자`, `VC 보증서`는 첫 등장에 `등록 보증서(VC)`, `원본`은 가능한 한 `등록 영상`으로 통일한다.
- 홈페이지는 이해와 시작, 검증 웹은 입력과 결과, 개발자 센터는 상세 구현에 집중한다.

## 7. 더 강한 표현을 사용하기 전에 필요한 확인

### 구현과 설명을 맞춰야 하는 지점

1. **시각의 의미:** API의 `registeredAt`은 `Video.create`에서 만든 서버 시각이다. 컨트랙트의 `block.timestamp`와 동일한 값이라고 설명하지 않는다.
2. **서명의 주체:** 등록 기록의 `signature`는 서버 HMAC이다. 등록자가 자신의 개인키로 직접 서명한 영상 증명으로 설명하지 않는다. VC 서명과도 구분한다.
3. **보증서 확인 경로:** 저장된 credential JSON이 있으면 SDK 서명 검증을 수행한다. 없으면 발급 원장의 상태·클레임을 확인하는 경로다. 모든 레코드를 동일한 독립 검증 방식으로 처리한다고 표현하지 않는다.
4. **온체인 결속 범위:** 대표 지문은 `SHA-256(perceptualHash + fineHash)`다. 별도로 저장하는 세그먼트 영상·음성 지문이 모두 이 값에 직접 포함되는 구조는 아니다. “모든 비교 데이터가 온체인으로 보호된다”는 표현은 피한다.
5. **검증 경로의 추가 기술 검토:** `verifyOnBlockchain`은 저장된 대표 지문으로 기록을 조회하고 HMAC을 대조한다. 제출 파일·현재 DB 해시에서 대표 지문을 재계산해 끝까지 연결하는 검증이 충분한지는 별도 보안 검토 대상으로 남긴다.
6. **최신성:** 정확 일치 결과 등에 10분 캐시가 있다. 보증서 외부 상태 변경의 즉시 반영이나 매 요청 실시간 조회를 보장하는 문구는 쓰지 않는다.
7. **문서 드리프트:** 백엔드 README의 `verify:v3:`와 실제 `verify:v1:result:` 캐시 키가 다르다. README가 참조하는 `docs/video-verification.md`는 현재 로컬 경로에서 찾지 못했다.
8. **URL 비교 설명:** 파일과 URL은 같은 지문 생성 서비스와 비교 로직을 사용한다. 웹 FAQ의 “URL이라 더 정밀한 프레임 비교”는 현재 코드로 입증되지 않는다.

이는 홈페이지 문구의 근거와 범위를 점검한 결과이며, 보안 감사나 취약점 악용 검증 결과는 아니다.

### 공개 전에 확인할 운영·성능 항목

- 홈페이지의 각 버튼이 의도한 기능 화면에 도착하는지 확인.
- 웹 파일·URL, 확장, 카카오톡의 실제 배포 환경에서 정상·미등록·장애 응답 확인.
- iOS 공개 배포 여부와 확장 ZIP 버전·원본 코드의 대응 확인.
- 정확 일치, 재인코딩, 자르기, 음성 교체, 미등록, 보증서 없음, 비활성화, 외부 장애의 결과 예시 확보.
- 검증 속도나 탐지 정확도를 공개하려면 입력 조건·표본·실패 사례를 포함한 별도 측정 필요.

영상 변형 비교 테스트와 판정·캐시·VC 테스트 코드는 존재한다. 이번 내용 검토에서는 테스트를 실행하지 않았으며, 테스트 존재를 운영 성공률이나 딥페이크 탐지 정확도의 근거로 사용하지 않았다.

## 8. 구현 순서와 완료 기준

1. **핵심 문안과 용어 정리:** 첫 화면·필요성·사용 과정·검증 원리를 위 문안으로 재구성. 완료 기준: 첫 화면만 읽어도 사전 등록 영상을 비교하는 서비스임을 알 수 있음.
2. **결과 해석 강화:** 실제 응답 필드에 맞춘 예시 카드와 두 비교 방식 설명. 완료 기준: 정확 일치·유사도·미등록·오류를 구별하고 미등록을 가짜로 읽지 않음.
3. **채널 안내 정합성:** 웹 URL 지원, 앱 공개 상태, 확장 설치, 카카오톡 운영 상태 반영. 완료 기준: 버튼과 안내가 실제 이용 가능한 흐름과 일치.
4. **상세 문서 정리:** 해시·임계치·서명·시각·캐시·VC 검증 경계를 개발자 문서와 맞춤. 완료 기준: 본문·API 설명·현재 구현 사이의 불일치 해소.
5. **화면 검수:** 모바일과 데스크톱에서 문장 줄바꿈, 대비, 결과 예시, 링크, 빌드 확인.
